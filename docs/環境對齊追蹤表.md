> [!CAUTION]
> **「編碼」這項的驗收標準已經換過，舊指令會給你假綠。** 原本檢查 `sys.getdefaultencoding()` 與 `sys.stdout.encoding`，但這兩個都測不到真正的風險：
>
> - `sys.getdefaultencoding()` 在 Python 3 **恆為 `utf-8`**，沒有鑑別力。
> - `sys.stdout.encoding` 只反映 console 的 code page，換個終端機就變。
> - 真正決定 `open()` 不指定 `encoding` 時用什麼的，是 **`locale.getpreferredencoding(False)`**。
>
> C 在 2026-09-19 實測到的正是這個落差：`getdefaultencoding` 與 `stdout` 都是 `utf-8`，舊標準判定通過，但 `getpreferredencoding` 是 **`cp950`**——讀中文語料照樣會炸。根因是 `PYTHONUTF8` 沒設，設完才會變 `utf-8`。
>
> A 欄的 ✅ 原本是用舊指令量的，已於 2026-09-19 用新指令覆核：`locale.getpreferredencoding(False)` = `utf-8`，結論成立。
>
> 補充一個從 A 這邊得到的旁證：macOS 上三個值**全部**是 `utf-8`，連 `LC_ALL=C` 都一樣。也就是說舊標準的缺陷在 macOS 上根本看不出來——這正是它當初被訂下來的原因，也說明為什麼跨平台的驗收標準不能只在一種系統上想。
>
> **`setx` 只對「之後開的」行程生效。** 剛跑完 `setx PYTHONUTF8 1` 的那個視窗再測一次，還是會看到 `cp950`——這不是沒設成功，是舊行程讀不到新的環境變數。**關掉終端機重開再測**，否則你會以為自己修失敗了。C 欄的 ✅ 是依這個方式確認的。

## 🔴 Windows 安裝踩過的坑（D 於 2026-09-19 實測，B 已重現坑 1；E 很可能也會遇到）

### 坑 1：`uv` 裝 Python 3.11 時中斷

```
error: Missing expected target directory for Python minor version link
```

**Python 其實已經完整下載好了**，壞的只是 uv 建立「次版本捷徑」那一步（uv 0.12.17 在 Windows 的 bug）。

確認方式——直接執行那個 python.exe，印得出版本就代表 Python 沒問題：

```
C:\Users\<帳號>\AppData\Roaming\uv\python\cpython-3.11.16-windows-x86_64-none\python.exe --version
```

繞過方式——`uv sync` 指定完整路徑：

```
uv sync --extra dev --extra ui --python "C:\Users\<帳號>\AppData\Roaming\uv\python\cpython-3.11.16-windows-x86_64-none\python.exe"
```

裝好之後 `uv run` 完全正常，**這個 bug 只影響第一次安裝**。

> [!NOTE]
> **B 於 2026-09-19 在另一台 Windows 上完整重現了坑 1**，同樣是 uv 0.12.17、同樣的錯誤訊息，
> 照上面的繞道方式（`uv sync` 指定完整路徑）處理後一切正常。
> 這支持 D 的判斷：問題出在 uv 0.12.17 在 Windows 的 bug，不是個別機器的狀況。
> **E 後來改用下面那種繞法，全程沒有踩到這個坑。**
>
> 坑 2 沒有遇到——專案放在 `C:\Users\<帳號>\Desktop\git\`，從磁碟機代號到最後一層都是英數。

**另一種繞法（E 於 2026-09-19 實測）——換掉 uv 放 Python 的位置，設一次永久解決：**

```
setx UV_PYTHON_INSTALL_DIR "%USERPROFILE%\.uv-python"
```

設完**要重開終端機**才生效，然後 `uv python install 3.11` 就會成功。

問題出在 `AppData\Roaming` 這條路徑本身——uv 在那裡建立的次版本 junction，用
PowerShell 的 `Test-Path` 驗證是通的，但 uv 自己讀不回來（同一版 0.12.17）。
換成 `%USERPROFILE%\.uv-python` 之後一次就裝成功，全程沒有踩到這個坑。

兩種繞法的差別：指定 `--python` 完整路徑**每次 `uv sync` 都要記得打**，
換安裝目錄則是設定一次、之後所有專案都不用再管。新加入的人建議直接用後者。

### 坑 2：專案路徑含中文 → Python 完全無法啟動

```
UnicodeDecodeError: 'cp950' codec can't decode byte 0xe6
Fatal Python error: init_import_site: Failed to import the site module
```

venv 裡的 `_editable_impl_anti_fraud_copilot.pth` 用 UTF-8 存專案路徑，Python 啟動時卻用
locale 編碼（cp950）讀它 → 路徑有中文就直接死在 `site` 模組，連 `uv run` 都起不來。

**`PYTHONUTF8=1` 救不了**——uv 以隔離模式呼叫直譯器，會忽略 `PYTHON*` 環境變數。
改系統地區設定可解，但需要管理員權限。

**所以：放專案的資料夾，從磁碟機代號到最後一層，只能用英文、數字、底線。**
D 原本放在 `C:\Users\<帳號>\我的本機資料\`，因為這個坑搬到 `C:\Users\<帳號>\Dev\`。

E 依此建議，一開始就 clone 到 `C:\Users\<帳號>\Dev\`，未踩到這個坑——這條建議有效，**新加入的人照做即可，不要等踩到才搬**。

## 📊 Kaggle 免費 GPU 跑 Ollama（D 於 2026-09-19 實測可行）

沒有合用顯卡的人可以走這條路。Kaggle 免費額度：GPU 30 小時／週（T4 ×2，各 16GB）、
記憶體 30GB、單次 session 最長 12 小時、需手機驗證、不需信用卡。

```python
import subprocess, time, requests
subprocess.run("apt-get -qq install -y zstd", shell=True, check=True)   # Kaggle 沒有 zstd，少這行會失敗
subprocess.run("curl -fsSL https://ollama.com/install.sh | sh", shell=True, check=True)
subprocess.Popen(["ollama","serve"], stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
time.sleep(8)
print(requests.get("http://127.0.0.1:11434").text)   # Ollama is running
subprocess.run("ollama pull qwen2.5:3b", shell=True, check=True)
subprocess.run("nvidia-smi --query-gpu=name,memory.used --format=csv", shell=True)
```

安裝時會出現 `systemd is not running` 與 `Unable to detect NVIDIA/AMD GPU` 兩個 WARNING，
**都可以忽略**——實測 `nvidia-smi` 顯示 `Tesla T4, 3329 MiB`，模型確實跑在 GPU 上。

> [!CAUTION]
> **這個 3329 MiB 是 T4（16GB）上的數字，不能直接套到 4GB 卡。**
> Ollama 會依可用 VRAM 調整配置，B 在真正的 GTX 1650 / 4GB 上實測只佔 **2127 MiB**（見下一節）。
> 原本據此推論的「4GB 卡有溢出風險」**結論要修正**：風險是推論變慢，不是跑不動。
> `model-lock.md` 的「4GB 卡實際可用約 3–3.5 GB」這個估計也偏保守，建議 S3 正式鎖定前一併檢視。

## 📊 4GB 卡實測：qwen2.5:3b 的 VRAM 與 context 門檻（B 於 2026-09-19 實測）

上一節 D 的數字量在 Kaggle 的 T4（16GB）上，但 B／C／D 的卡是 4GB。
B 直接在 **GTX 1650 / 4GB** 上量了一輪，逐段拉大 context：

| `num_ctx` | VRAM（`nvidia-smi`） | `ollama ps` 配置 |
|---|---|---|
| 4096（預設） | 2127 MiB | **100% GPU** |
| 8192 | 2277 MiB | **100% GPU** |
| 16384 | 2283 MiB | 21%/79% CPU/GPU |
| 32768 | 2259 MiB | 35%/65% CPU/GPU |

**兩個結論：**

1. **實際佔用比 T4 的 3329 MiB 低約 1.2 GB。** Ollama 會依可用 VRAM 調整配置，
   所以 16GB 卡上的量測值**不能**當成 4GB 卡的預測值——這兩個數字不是同一件事。
2. **超過門檻不會 OOM 崩潰，而是把層數卸載給 CPU。** `nvidia-smi` 的數字始終停在
   2.1～2.3 GB 就是這個原因：Ollama 寧可降速也不會撐爆 VRAM。
   所以 4GB 卡的風險性質是**推論變慢**，不是**跑不動**。

**門檻落在 `num_ctx` 8192 與 16384 之間。** S13 要求 prompt 放 12 則以上示範題，
把 context 壓在 **8192 以內**就能維持 100% GPU。

> [!NOTE]
> **這台的螢幕走 AMD 內顯，GTX 1650 幾乎整張讓給模型。**
> 單顯卡的機器（螢幕也吃 1650）可用 VRAM 會再少一些，門檻可能落在 8192 以下。
> C 是同型號的卡，回報時值得順手驗證這一點。

### VRAM 與 context 的關係（E 於 2026-09-19 在 RTX 5070 Ti 實測）

上面那個 3329 MiB 讓人擔心 4 GB 卡會爆，但**佔用量幾乎全由 `num_ctx` 決定**。
同一顆模型、同一個量化，只改 context 長度：

| `num_ctx` | `ollama ps` SIZE | GPU 實際增量 | 4 GB 卡 |
|---:|---:|---:|:--|
| 4,096（Ollama 預設） | 2.2 GB | 2,284 MiB | 安全 |
| 8,192 | 2.4 GB | 2,531 MiB | **安全，建議用這個** |
| 16,384 | 2.7 GB | 2,814 MiB | 仍有餘裕 |
| 32,768（模型上限） | 3.4 GB | 3,433 MiB | **危險，接近 D 量到的 3,329 MiB** |

也就是說，**D 在 Kaggle 量到的 3.3 GB 對應的是把 context 開到最大，不是實際會用的設定。**

那 S13 需要多大？以 Qwen2.5 的中文 token 密度實測 **1 字 ≈ 0.83 token**（346 字的虛構敘述 → 286 token）推算：

| 示範題數 | prompt | 含輸出預留 |
|---:|---:|---:|
| 12 則 | 約 3,461 token | 約 4,261 token |
| 16 則 | 約 4,453 token | 約 5,253 token |
| 20 則 | 約 5,445 token | 約 6,245 token |

**結論：`num_ctx` 固定 8,192。** 4,096 放不下 12 則示範題（S13 的下限就會超），8,192 連 20 則都還有餘裕，而且只吃 2.4 GB——離 4 GB 卡的可用上限還有約 1 GB。

> [!NOTE]
> 這組數字是在 16 GB 卡上量的，量到的是**模型本身要多少**，不是「大卡才跑得動」。
> 4 GB 卡的風險不在模型大小，而在 `num_ctx` 設太大。建議 S13 在呼叫 SLM 時
> **明確指定 `num_ctx`，不要依賴預設值**——預設 4,096 反而會讓示範題放不完整。
