> [!CAUTION]
> **「編碼」這項的驗收標準已經換過，舊指令會給你假綠。** 原本檢查 `sys.getdefaultencoding()` 與 `sys.stdout.encoding`，但這兩個都測不到真正的風險：
>
> - `sys.getdefaultencoding()` 在 Python 3 **恆為 `utf-8`**，沒有鑑別力。
> - `sys.stdout.encoding` 只反映 console 的 code page，換個終端機就變。
> - 真正決定 `open()` 不指定 `encoding` 時用什麼的，是 **`locale.getpreferredencoding(False)`**。
>
> C 在 2026-09-19 實測到的正是這個落差：`getdefaultencoding` 與 `stdout` 都是 `utf-8`，舊標準判定通過，但 `getpreferredencoding` 是 **`cp950`**——讀中文語料照樣會炸。根因是 `PYTHONUTF8` 沒設，設完才會變 `utf-8`。
>
> A 欄的 ✅ 原本是用舊指令量的，已於 2026-09-19 用新指令覆核：`locale.getpreferredencoding(False)` = `utf-8`，結論成立。
>
> 補充一個從 A 這邊得到的旁證：macOS 上三個值**全部**是 `utf-8`，連 `LC_ALL=C` 都一樣。也就是說舊標準的缺陷在 macOS 上根本看不出來——這正是它當初被訂下來的原因，也說明為什麼跨平台的驗收標準不能只在一種系統上想。
>
> **`setx` 只對「之後開的」行程生效。** 剛跑完 `setx PYTHONUTF8 1` 的那個視窗再測一次，還是會看到 `cp950`——這不是沒設成功，是舊行程讀不到新的環境變數。**關掉終端機重開再測**，否則你會以為自己修失敗了。C 欄的 ✅ 是依這個方式確認的。

## 沒裝 uv 的備援（僅 Windows）

```bat
py -3.11 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

> [!CAUTION]
> 這是備援不是正規做法。`requirements.txt` 是手寫的 `uv.lock` 鏡像，保證得了「裝起來能跑」，保證不了「五台機器完全一樣」——那件事只有 `uv.lock` 做得到。CI 的「相依同步檢查」會盯著這兩份不要走散。
