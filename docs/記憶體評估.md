# 記憶體整體評估

> 一句話：現在這套在 16 GB 的機器上跑得動（尖峰約 3.5 GB ＋ Ollama 2.4 GB），
> 但**最大的一筆不是語料也不是索引，是 fp32 的 bge-m3（1.9 GB）**。
> 真正要擔心的是五個模組都接上向量庫之後的加總。
>
> **2026-09-27 做了三項改善**（見[第七節](#七2026-09-27-做的三項改善)）：
> 開機從 314 MB 降到 116 MB、開機高水位從 572 MB 降到 130 MB。

**量測條件**：2026-09-27，A 的機器（Apple M5、16 GB 統一記憶體、macOS 25.6），
分支 `a-model`。量的是行程的實際 RSS（`ps -o rss=`），每一步之前先 `gc.collect()`；
高水位用 `ru_maxrss`。不是檔案大小，也不是 `ru_maxrss` 當成當下值（那是常見的
量錯方式 —— 高水位只會漲不會跌，會把後面載入的東西吃掉看不見）。

## 一、完整軌跡（Streamlit 那個 Python 行程）

| 階段 | 當下 RSS | 增量 | 行程高水位 |
|---|---|---|---|
| 起始（乾淨的 Python） | 17 MB | | 17 MB |
| import 外殼與 contracts | 32 MB | +14 | 32 MB |
| `load("all")`：掃模組＋跑 health | **115 MB** | +84 | 130 MB |
| 預熱 bge-m3（fp32、CPU） | **2,054 MB** | **+1,938** | 2,054 MB |
| A `analyze()`（載入語料＋對映索引） | 2,477 MB | +423 | 2,478 MB |
| C `analyze()`（載入 C 的語料與索引） | 2,724 MB | +247 | 2,753 MB |
| 第一張截圖：載入 OCR 引擎 | 3,056 MB | +332 | 3,056 MB |
| 再辨識 19 張截圖 | **3,500 MB** | +444 | **3,500 MB** |

加上 Ollama 那個行程的 qwen2.5:3b（Q4_K_M，約 2.4 GB，閒置 5 分鐘卸載），
**全系統尖峰約 5.9 GB**。16 GB 的機器用掉三分之一多一點。

這張表是 2026-09-27 三項改善**之後**量的。改善前的對照：開機 314 MB
（高水位 572）、全部跑完約 3,528 MB。

## 二、開機不再載語料（改善後）

`load("all")` 會跑每個模組的 `health()`。A 的 `health()` 原本呼叫兩次
`load_local()` ——整份 78 MB 讀進來、解析成 81,423 個物件，只為了取一個 bool。
配上 2026-09-27 加的語料快取，那份語料還會從開機一路留到關機。

改成 `count_local()`：二進位分塊數 `b"\n"`，25 ms、記憶體幾乎不動
（`load_local()` 是 185 ms）。**開機從 314 MB 降到 115 MB，開機高水位從
572 MB 降到 130 MB。** health 的顯示反而更有用了 —— 從空字串變成「81,423 筆」。

語料改成第一次查詢才載。代價是那次解析發生在 bge-m3（1.9 GB）已經在記憶體裡
的時候，配置器比較難把暫存還給系統：實測跑完整輪之後多留 106 MB。
**這個代價被第三項改善（串流解析）抵銷掉了**，見第七節。

## 三、OCR 引擎：會長，但會停

用 90 張內容雜湊都不同的截圖逼快取從空到滿（上限 64 筆），在一個沒有載入
bge-m3 的乾淨行程裡量：

| 第幾張 | RSS | 較 OCR 前 | 快取筆數 |
|---|---|---|---|
| 1 | 571 MB | +497 | 1 |
| 5 | 739 MB | +664 | 5 |
| 10 | 778 MB | +703 | 10 |
| 20 | 1,010 MB | **+935** | 20 |
| 30 / 40 / 50 | 1,010～1,019 MB | +935～944 | 30／40／50 |
| 64（快取滿） | 1,019 MB | +944 | 64 |
| 70 / 80 | 1,019 MB | +944 | 64 |
| 90 | 621 MB | +546 | 64 |

**在第 20 張左右就停住了**，不是跟著快取長到 64 張 —— 所以長的不是我們存的
辨識結果（那只是文字與座標，很小），是 onnxruntime 自己的記憶體池。第 90 張
掉回 621 MB 是配置器把頁面還給系統。

主要架構圖上寫的是「跑久了約 1.5 GB」。**我量不到那個數字**：單獨跑是 +0.95 GB
封頂，在完整的 App 裡（bge-m3 與索引都已載入）辨識 20 張只加了 455 MB。
那個 1.5 GB 可能是別台機器、或別的條件量的，但照這裡的量測它偏高。

## 四、逐項拆解

| 項目 | 常駐 | 備註 |
|---|---|---|

| A 的索引 `vectors.npy` | 334 MB | 81,423 × 1024 × 4 bytes。改用 `mmap_mode="r"` 之後是檔案對映：沒碰到的頁不佔，碰過的頁記憶體吃緊時可以被回收 |
| A 的語料（81,423 筆 `Case`） | 112 MB | 檔案 75 MB；改成串流解析之後從 197 MB 降下來 |
| OCR 引擎（PP-OCRv6 small） | 約 500～950 MB | 見第三節 |
| C 的語料＋索引 | 95 MB | 10,051 筆、`vectors.npz` 60 MB |
| 外殼＋套件 import | 約 100 MB | pydantic、numpy、yaml… |
| qwen2.5:3b（另一個行程） | 2,400 MB | Ollama，閒置 5 分鐘卸載 |

## 五、風險：五個模組都接上向量庫之後

現在只有 A、C 有向量庫，E 這台沒有語料檔，B、D 還是空殼。如果其餘三個都照
A 現在的規模做（不做標籤切片、八萬筆上下），以改善後的單模組成本推估：

| | 每個模組 | 五個 |
|---|---|---|
| 索引 `vectors.npy` | 334 MB（檔案對映，可回收） | 1.7 GB |
| 語料（`Case` 物件） | 112 MB | 0.6 GB |
| 小計 | 446 MB | **2.2 GB** |

加上 bge-m3 1.9 GB、OCR 約 0.95 GB、外殼與套件 0.1 GB ≈ **5.2 GB**，
再加 Ollama 的 2.4 GB → **約 7.6 GB**。

16 GB 的機器撐得住，8 GB 的是紅線。但有兩件事讓這個推估不至於太糟：

- **語料不再開機全部載入**（第七節第一項），只有真的被路由選中、跑過
  `analyze()` 的模組才會載自己那份
- **索引是檔案對映**（第七節第二項），沒碰到的頁不佔實體記憶體，碰過的頁在
  記憶體吃緊時可以被作業系統回收 —— 匿名記憶體只能換到 swap

換句話說「五個模組同時滿載」是上界，不是常態：路由一次只交給一個模組。

## 六、結論

- **現在沒問題**：尖峰 3.5 GB ＋ Ollama 2.4 GB，16 GB 的機器用掉三分之一多一點
- **最大的一筆是 bge-m3 的 1.9 GB**，而那是 fp32 的決議換來的，不是浪費
- **要注意的是加總**：五個模組都上向量庫之後約 7 GB，對 8 GB 的機器是紅線
- **圖上「OCR 跑久了約 1.5 GB」偏高**，實測封頂在 0.95 GB
- **開機成本已經壓下來**：314 → 115 MB，高水位 572 → 130 MB

## 七、2026-09-27 做的三項改善

| 改動 | 量到的效果 |
|---|---|
| `health()` 改用 `count_local()`（數行數，不解析） | 開機 314 → 115 MB、開機高水位 572 → 130 MB |
| 索引改 `mmap_mode="r"` | 對映時 +0 MB（用到才進來）；放掉之後**完全歸還**，而 `np.load` 那版放掉後那 318 MB 仍留在行程裡 |
| `load_local()` 改逐行串流解析 | 語料常駐 197 → 112 MB、解析高水位 +258 → +112 MB、185 ms（原本 216 ms） |

第二項附帶一個必要的修正：`build_index()` 改成寫暫存檔再 `os.replace`。
就地覆蓋會在別人用 mmap 讀到一半時把底下的內容換掉；`os.replace` 是原子的，
而且換成新的 inode，舊的對映會繼續指著舊檔案直到失效重載。

三項都量過對查詢延遲沒有影響（mmap 甚至第一次還快一點：`np.load` 5 ms
＋第一次內積 18 ms，對上整份讀進來的 26 ms ＋ 4 ms）。

全部跑完的總量從 3,528 MB 變成 3,500 MB —— 穩態幾乎沒動，**省下來的都在開機
那一段**。那正是要省的地方：開機的瞬間峰值才是記憶體吃緊的機器會出事的地方。
