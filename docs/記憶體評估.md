# 記憶體整體評估

> 一句話：現在這套在 16 GB 的機器上跑得動（尖峰約 2.9 GB ＋ Ollama 2.4 GB），
> 但**最大的一筆不是語料也不是索引，是 fp32 的 bge-m3（1.9 GB）**。
> 真正要擔心的是五個模組都接上向量庫之後的加總。

**量測條件**：2026-09-27，A 的機器（Apple M5、16 GB 統一記憶體、macOS 25.6），
分支 `a-model`。量的是行程的實際 RSS（`ps -o rss=`），每一步之前先 `gc.collect()`；
高水位用 `ru_maxrss`。不是檔案大小，也不是 `ru_maxrss` 當成當下值（那是常見的
量錯方式 —— 高水位只會漲不會跌，會把後面載入的東西吃掉看不見）。

## 一、完整軌跡（Streamlit 那個 Python 行程）

| 階段 | 當下 RSS | 增量 | 行程高水位 |
|---|---|---|---|
| 起始（乾淨的 Python） | 17 MB | | 18 MB |
| import 外殼與 contracts | 32 MB | +14 | 32 MB |
| `load("all")`：掃模組＋跑 health | **314 MB** | +282 | 572 MB |
| 預熱 bge-m3（fp32、CPU） | **2,201 MB** | **+1,887** | 2,201 MB |
| A `analyze()`（載入 334 MB 索引） | 2,528 MB | +327 | 2,528 MB |
| C `analyze()`（載入 C 的語料與索引） | 2,622 MB | +95 | 2,741 MB |
| 第一張截圖：載入 OCR 引擎 | 2,480 MB | −142 | 2,741 MB |
| 再辨識 19 張截圖 | **2,936 MB** | +455 | **2,936 MB** |

加上 Ollama 那個行程的 qwen2.5:3b（Q4_K_M，約 2.4 GB，閒置 5 分鐘卸載），
**全系統尖峰約 5.3 GB**。16 GB 的機器用掉三分之一。

「載入 OCR 引擎」那一格是負的不是筆誤 —— 前一步 C 解壓 `.npz` 的暫存被釋放掉了，
剛好蓋過引擎本身的增量。要看引擎真正要多少，看下面第三節。

## 二、開機就付掉的那 282 MB：A 的語料

`load("all")` 會跑每個模組的 `health()`，而 A 的 `health()` 呼叫 `load_local()`。
2026-09-27 給 `load_local()` 加上快取之後，**這份語料從開機就一直留著**
（81,423 筆、197 MB），不再是「用完就放掉」。

這是那次改動刻意換來的：查詢延遲從 404 ms 降到 119 ms，代價是 197 MB 常駐。
在 16 GB 上划算，在更小的機器上未必。要退回去只要把 `m1_corpus._CACHE` 拿掉，
延遲會漲回去。

高水位 572 MB 比當下的 314 MB 高出 258 MB，那是解析 78 MB JSONL 時的暫態
（整份字串 ＋ `split("\n")` 的 list ＋ json 物件同時存在）。**開機瞬間的峰值
比穩態高一倍**，記憶體吃緊的機器會是在這裡出事，不是在穩態。

## 三、OCR 引擎：會長，但會停

用 90 張內容雜湊都不同的截圖逼快取從空到滿（上限 64 筆），在一個沒有載入
bge-m3 的乾淨行程裡量：

| 第幾張 | RSS | 較 OCR 前 | 快取筆數 |
|---|---|---|---|
| 1 | 571 MB | +497 | 1 |
| 5 | 739 MB | +664 | 5 |
| 10 | 778 MB | +703 | 10 |
| 20 | 1,010 MB | **+935** | 20 |
| 30 / 40 / 50 | 1,010～1,019 MB | +935～944 | 30／40／50 |
| 64（快取滿） | 1,019 MB | +944 | 64 |
| 70 / 80 | 1,019 MB | +944 | 64 |
| 90 | 621 MB | +546 | 64 |

**在第 20 張左右就停住了**，不是跟著快取長到 64 張 —— 所以長的不是我們存的
辨識結果（那只是文字與座標，很小），是 onnxruntime 自己的記憶體池。第 90 張
掉回 621 MB 是配置器把頁面還給系統。

主要架構圖上寫的是「跑久了約 1.5 GB」。**我量不到那個數字**：單獨跑是 +0.95 GB
封頂，在完整的 App 裡（bge-m3 與索引都已載入）辨識 20 張只加了 455 MB。
那個 1.5 GB 可能是別台機器、或別的條件量的，但照這裡的量測它偏高。

## 四、逐項拆解

| 項目 | 常駐 | 備註 |
|---|---|---|
| bge-m3（fp32） | **1,887 MB** | 最大的一筆。fp16 會少掉一半，但專案決議鎖 fp32 —— MPS 與 CUDA 的低位數值差異會讓五個人的分數不能互比 |
| A 的索引 `vectors.npy` | 334 MB | 81,423 × 1024 × 4 bytes |
| A 的語料（81,423 筆 `Case`） | 197 MB | 檔案只有 75 MB；Python 物件的額外開銷約 2.6 倍 |
| OCR 引擎（PP-OCRv6 small） | 約 500～950 MB | 見第三節 |
| C 的語料＋索引 | 95 MB | 10,051 筆、`vectors.npz` 60 MB |
| 外殼＋套件 import | 約 100 MB | pydantic、numpy、yaml… |
| qwen2.5:3b（另一個行程） | 2,400 MB | Ollama，閒置 5 分鐘卸載 |

## 五、風險：五個模組都接上向量庫之後

現在只有 A、C 有向量庫，E 這台沒有語料檔，B、D 還是空殼。如果其餘三個都照
A 現在的規模做（不做標籤切片、八萬筆上下）：

- 每個模組約 531 MB（索引 334 ＋ 語料 197）
- 五個就是 **2.7 GB**，加上 bge-m3 1.9 GB、OCR 0.95 GB、外殼 0.1 GB ≈ **5.6 GB**
- 再加 Ollama 2.4 GB → **約 8 GB**

16 GB 的機器還撐得住，8 GB 的就不行了。而且**語料會在開機時全部載入**
（每個模組的 `health()` 都讀自己那份），所以開機的暫態峰值會更難看 ——
A 一個模組就讓峰值比穩態高 258 MB。

兩個便宜的緩解，都還沒做：

1. **`health()` 不要讀全部語料**。它只需要知道「語料檔在不在、有幾筆」，
   現在卻是整份解析。改成只數行數，開機成本幾乎歸零。
   （A 的 `module.py` 還連續呼叫 `load_local()` 兩次，有快取之後第二次免費，
   但那是拿記憶體換的。）
2. **索引用 `mmap_mode="r"`**。`vectors.npy` 是唯讀的，記憶體對映之後由作業系統
   決定要留多少頁在實體記憶體，多個模組的索引就不會同時硬佔。代價是第一次
   查詢會慢一點。A 的 334 MB 現在是實實在在佔著的。

## 六、結論

- **現在沒問題**：尖峰 2.9 GB ＋ Ollama 2.4 GB，16 GB 的機器用掉三分之一
- **最大的一筆是 bge-m3 的 1.9 GB**，而那是 fp32 的決議換來的，不是浪費
- **要注意的是加總**：五個模組都上向量庫之後約 8 GB，對 8 GB 的機器是紅線
- **圖上「OCR 跑久了約 1.5 GB」偏高**，實測封頂在 0.95 GB
