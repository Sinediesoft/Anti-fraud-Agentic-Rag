## 硬體盤點（S2 第 5 點）

> [!CAUTION]
> 🔴 **混用環境必須多記「作業系統」與「模型後端」兩欄。**
> Apple Silicon 的**統一記憶體**與 NVIDIA 的**顯卡記憶體**不是同一個東西：
> M 系列 16GB 統一記憶體大約可跑 7B 量化模型，與 8GB 顯卡記憶體的 Windows 機相當。
> 兩種數字都要記下來再一起判斷「最低配那台」是誰。

| 成員 | 作業系統 | 模型後端 | 顯示卡 / 晶片 | 顯卡或統一記憶體 | 系統記憶體 | 盤點日期 |
|---|---|---|---|---|---|---|
| A | macOS 26.6.2 | Metal | Apple M5（10 核：4P+6E） | **16 GB 統一記憶體**（GPU 實際可用約 10–11 GB） | 同左（統一） | 2026-09-19 |
| B | Windows | CUDA | GTX 1050 Ti（Pascal, 無 Tensor Core） | **4 GB** | TODO | 2026-09-19 |
| C | Windows | CUDA | GTX 1650（Turing TU117, 無 Tensor Core） | **4 GB** | TODO | 2026-09-19 |
| D | Windows | CUDA | GTX 1650（Turing TU117, 無 Tensor Core） | **4 GB** | TODO | 2026-09-19 |
| E | Windows | CUDA | RTX 5070 Ti（Blackwell） | **16 GB** | TODO | 2026-09-19 |

> [!CAUTION]
> 🔴 **全隊天花板 = 4 GB**（B / C / D 三台）。
> 說明書 S2：「顯卡記憶體不夠時，正確做法是**五個人一起改用小模型**，
> 不是有顯卡的用大的。那會直接違反規矩，分數就不能比了。」
>
> 🔴 **E 的 5070 Ti 有 16 GB，但不能自己用大模型。** A 的 M5 同理。

**還缺**：B / C / D / E 的系統記憶體（RAM）。顯卡不夠時會退到 CPU，而且嵌入與
重排序本來就固定跑 CPU，低於 8 GB 會很痛。請四位補上。

## 🔴 模型尺寸決策（依 4 GB 天花板推導）

4 GB 顯卡不是只放模型——還要放 KV cache 與上下文。實際可用大約 3–3.5 GB。

| 尺寸 | 代表模型 | 檔案(Q4_K_M) | A (16G) | B (4G) | C/D (4G) | E (16G) | 結論 |
|---|---|---|---|---|---|---|---|
| 7B | Qwen2.5-7B / TAIDE-LX-7B | ~4.5–4.7 GB | ✅ | ❌ 溢出 | ❌ 溢出 | ✅ | 🔴 三人退 CPU，慢到不能展示 |
| **3B** | **Qwen2.5-3B** | **~1.9 GB** | ✅ | ✅ | ✅ | ✅ | 🟢 **全員 GPU 都跑得動** |

### 建議（待 S3 全員決議，尚未鎖定）

**地端 SLM：Qwen2.5-3B-Instruct，Q4_K_M 量化**

說明書列的候選是 Qwen2.5-7B、Llama-3.2-3B、TAIDE-LX-7B。在 4 GB 天花板下：

| 候選 | 為什麼不行 |
|---|---|
| Qwen2.5-7B | 尺寸超標 |
| TAIDE-LX-7B | 尺寸超標（可惜，它是專為繁中訓練的） |
| Llama-3.2-3B | 尺寸 OK，但 🔴 **官方支援語言不含中文**，處理繁中受害者敘述會吃虧 |

所以建議偏離清單一格用 **Qwen2.5-3B**——同一個家族、只是換尺寸，中文能力遠勝
Llama-3.2-3B。**這個偏離要全員同意並寫進報告**，理由可以直接寫：
「硬體天花板是 4 GB，而說明書清單內唯一合尺寸的模型不支援中文。」

### 老顯卡的疑慮（已確認不成問題）

| 疑慮 | 答案 |
|---|---|
| GTX 1050 Ti (Pascal) 還能跑嗎 | ✅ Ollama / llama.cpp 仍支援，只是沒有 Tensor Core，速度普通 |
| GTX 1650 沒有 Tensor Core | ✅ 跑 3B Q4 沒問題 |
| 要自己裝 CUDA Toolkit 嗎 | ❌ 不用，Ollama 的 Windows 安裝檔自帶執行時期 |
| 老顯卡會影響分數嗎 | ✅ **完全不會**——嵌入與重排序釘死在 CPU + fp32，決定分數的路徑根本不上 GPU |

這是「釘死 CPU」那個決議的額外好處：五張差異極大的顯卡（4 GB 到 16 GB、Pascal 到
Blackwell）完全不影響分數可比性。

## ⚠️ 已知風險：重排序可能撞到 S12 的延遲門檻

S12 要求**查詢延遲 p95 ≤ 1 秒**，而流程是「用重排序模型把前 50 筆重排」。

bge-reranker-v2-m3 約 5.6 億參數，在 **CPU fp32** 上跑 50 筆 query-document 配對，
**很可能超過 1 秒**——尤其在 B / C / D 那種較舊的筆電 CPU 上。

這是「釘死 CPU」與延遲門檻之間的潛在衝突。**現在不用決定，S12 實測後再選**：

| 解法 | 代價 |
|---|---|
| 只重排前 20 筆而不是 50 筆 | 可能少抓到一點 Recall |
| 改用較小的 bge-reranker-base | 準確度略降 |
| 重排序改用 ONNX int8 量化版跑 CPU | 多一道轉換，但跨機器仍然一致 |
| 分數表分開記「含重排序」與「不含重排序」 | 最誠實，也符合說明書要求對照組的精神 |

**不要到第四週才發現門檻過不了。**

## 🔴 跨平台決議（S3 鎖定時一併寫死）

> [!CAUTION]
> **嵌入模型與重排序模型固定 `device="cpu"`、`dtype=float32`。**
>
> 同一個模型在 Mac 的 MPS（預設 fp16）與 Windows 的 CUDA/CPU（fp32）上算出來的向量
> 有低位數值差異，分數接近時可能讓 **Recall@5 差一兩個百分點** ——
> 那就違反了「五個人的分數要能互相比較」這個前提。
>
> 成本很低：嵌入只在建索引時跑一次（幾千筆，CPU 幾分鐘）與每次查詢一句話（毫秒級）。

**地端 SLM 相反 —— 走各自 OS 的原生 Ollama，用自己的 GPU：**

| 系統 | Ollama 安裝 | 後端 |
|---|---|---|
| macOS | `brew install ollama` 或官網安裝檔 | Metal |
| Windows | 官網安裝檔（原生支援，不需要 WSL） | CUDA 或 CPU |

兩邊 `ollama pull` 同一份模型、對同一個編號，程式統一透過
`OLLAMA_HOST=http://127.0.0.1:11434` 連過去。
🔴 **不要把地端模型放進 Docker** —— Docker Desktop for Mac 傳不了 Metal，容器內只有 CPU。

詳見 [說明書補充：跨平台差異](說明書補充-跨平台差異.md)。
