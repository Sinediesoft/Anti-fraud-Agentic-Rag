| 尺寸 | 代表模型 | 檔案(Q4_K_M) | A (16G) | B (4G) | C/D (4G) | E (16G) | 結論 |
|---|---|---|---|---|---|---|---|
| 7B | Qwen2.5-7B / TAIDE-LX-7B | ~4.5–4.7 GB | ✅ | ❌ 溢出 | ❌ 溢出 | ✅ | 🔴 三人退 CPU，慢到不能展示 |
| **3B** | **Qwen2.5-3B** | **~1.9 GB** | ✅ | ✅ | ✅ | ✅ | 🟢 **全員 GPU 都跑得動** |

### 建議（待 S3 全員決議，尚未鎖定）

**地端 SLM：Qwen2.5-3B-Instruct，Q4_K_M 量化**

說明書列的候選是 Qwen2.5-7B、Llama-3.2-3B、TAIDE-LX-7B。在 4 GB 天花板下：

| 候選 | 為什麼不行 |

「硬體天花板是 4 GB，而說明書清單內唯一合尺寸的模型不支援中文。」

## 🔴 已實測確認：重排序在 CPU fp32 下**過不了** S12 門檻

> 本節原本寫的是「**可能**撞到門檻，S12 實測後再選」。2026-09-19 已在 C 的機器上實測，
> 結論要改寫：不是可能，是**差了一到兩個數量級**，而且原本列的退路**全部不夠**。

S12 要求**查詢延遲 p95 ≤ 1 秒**，流程是「用重排序模型把前 50 筆重排」。

### 實測條件

| 項目 | 值 |
|---|---|
| 機器 | C：i5-9300H（4 核 8 緒 @2.4GHz，2019 筆電）、11.9 GB RAM |
| 模型 | bge-reranker-v2-m3（實測 568M 參數） |
| 設定 | `device="cpu"`、`dtype=float32`，即本文件的跨平台決議 |
| 後端 | torch 2.14.0+cpu，4 執行緒 |
| 冷啟動載入 | **30.5 秒**（模型已在本機快取，不含下載） |

### 結果：只算重排序這一段的耗時

| 文件長度 | 前 50 筆 | 前 20 筆 | 前 10 筆 |
|---|--:|--:|--:|
| 短（~60 token） | 17.2 s | 6.8 s | 3.4 s |
| 中（~118 token） | 27.8 s | 10.8 s | 5.2 s |
| **長（~288 token，接近真實切塊）** | **57.2 s** | **23.2 s** | **13.0 s** |

> [!CAUTION]
> **沒有任何一格低於 1 秒。** 最寬鬆的組合（只重排 10 筆、文件短到 60 token）
> 仍是 3.4 秒；貼近真實 RAG 切塊長度的現行規劃（50 筆 × 288 token）是 **57 秒，
> 超標 57 倍**。而且這**只算重排序**，實際查詢還要加上向量檢索與 SLM 生成。

### 原本列的退路，逐條核對

| 解法 | 實測後的判定 |
|---|---|
| 只重排前 20 筆 | ❌ **不夠**。288 token 下仍是 23.2 秒，超標 23 倍 |
| 只重排前 10 筆 | ❌ **不夠**。13.0 秒，超標 13 倍 |
| 截短文件（`max_length` 512→256） | ❌ **幾乎無效**。瓶頸是實際 token 數，不是上限設定 |
| 改用 bge-reranker-base | ⚠️ 未實測。參數量約為 large 的一半、層數減半，估計快 3–4 倍 → 仍在 15 秒量級 |
| ONNX int8 量化 | ⚠️ 未實測。CPU 上一般快 2–4 倍 → 單用仍不夠 |
| 分數表分開記「含／不含重排序」 | ✅ **唯一不需額外工程就成立的選項** |

**三種加速疊起來**（base × int8 × 前 10 筆 × 短切塊）理論上有機會壓進 1 秒，
但那等於同時偏離說明書三次，且重排序只看 10 筆短文件時，它對 Recall 的貢獻也所剩無幾。

### 為什麼 GPU 救不了

直覺會想「那讓重排序上 GPU」，但在本隊的硬體下不成立：

- B / C / D 只有 4 GB VRAM，地端 SLM 已佔約 1.9 GB，放不下 fp32 的 2.27 GB 重排序模型。
- 改 fp16 才塞得下（約 1.13 GB），但那正是本文件釘死 CPU fp32 要避免的東西——
  Mac 的 MPS 與 Windows 的 CUDA 算出來的分數會有低位差異，**分數就不能互相比較了**。

### 待決議（S3 / S12）

這已經不是「調參數」能解決的，是**架構決策**，要全組決定：

1. **把重排序移出延遲路徑**，分數表分開記「含重排序」與「不含重排序」——最誠實，
   也符合說明書要求對照組的精神。延遲門檻由「不含重排序」那條負責。
2. **接受重排序離線化**：展示時預先算好，不在查詢當下跑。
3. **放棄重排序**，把力氣放在嵌入模型與切塊策略上。

> [!IMPORTANT]
> 這一題**在 B / C / D 上才看得見**。A 的 M5 與 E 的 5070 Ti 跑起來會快得多，
> 如果只有他們測過，這個門檻會一路矇混到第四週才爆。

**複現方式**：實測腳本未進儲存庫（torch 不在專案相依裡，且 `pyproject.toml`／`uv.lock`
是凍結的共管路徑）。要複現請用隔離環境，不要動專案相依：

```bash
uv run --no-project --python 3.11 --with torch --with transformers --with sentencepiece python bench.py
```

## 🔴 跨平台決議（S3 鎖定時一併寫死）

> [!CAUTION]
> **嵌入模型與重排序模型固定 `device="cpu"`、`dtype=float32`。**
>
> 同一個模型在 Mac 的 MPS（預設 fp16）與 Windows 的 CUDA/CPU（fp32）上算出來的向量
> 有低位數值差異，分數接近時可能讓 **Recall@5 差一兩個百分點** ——
> 那就違反了「五個人的分數要能互相比較」這個前提。
>
> 成本很低：嵌入只在建索引時跑一次（幾千筆，CPU 幾分鐘）與每次查詢一句話（毫秒級）。

**地端 SLM 相反 —— 走各自 OS 的原生 Ollama，用自己的 GPU：**

| 系統 | Ollama 安裝 | 後端 |
|---|---|---|
| macOS | `brew install ollama` 或官網安裝檔 | Metal |
| Windows | 官網安裝檔（原生支援，不需要 WSL） | CUDA 或 CPU |

兩邊 `ollama pull` 同一份模型、對同一個編號，程式統一透過
`OLLAMA_HOST=http://127.0.0.1:11434` 連過去。
🔴 **不要把地端模型放進 Docker** —— Docker Desktop for Mac 傳不了 Metal，容器內只有 CPU。

詳見 [說明書補充：跨平台差異](說明書補充-跨平台差異.md)。
