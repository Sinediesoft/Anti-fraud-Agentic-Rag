## §1.3 第一次設定（每個人只做一次）

### 🔴 補充：第 2 步「裝 Git」——Windows 要注意安裝選項

> [!CAUTION]
> Git for Windows 安裝過程中會問「Configuring the line ending conversions」。
> 預設是 **Checkout Windows-style, commit Unix-style**（`core.autocrlf=true`），
> 這會把 `Makefile` 轉成 CRLF，導致 `make` 直接爆 `missing separator`。
>
> **選 `Checkout as-is, commit Unix-style line endings`。**
> 已經裝好的人執行下面這行補救：
>
> ```bash
> git config --global core.autocrlf input
> ```

本 repo 已經放了 `.gitattributes` 把全 repo 釘死在 LF，**優先權高於個人設定**，所以就算忘了設也不會壞。但自己設一次比較保險。

### 🔴 補充：第 6 步「建環境」——uv 的安裝指令兩邊不同

說明書只寫「照 S2 的步驟安裝套件」，但 uv 本身的安裝方式不一樣：

| 系統 | 安裝 uv |
|---|---|
| macOS | `curl -LsSf https://astral.sh/uv/install.sh \| sh` 或 `brew install uv` |
| **Windows** | 🔴 **PowerShell 執行** `powershell -c "irm https://astral.sh/uv/install.ps1 \| iex"` |

裝完兩邊都一樣用 `uv --version` 確認。

## S2 五台電腦裝出一模一樣的環境

### 🔴 更正：第 4 步「寫 Makefile」——Windows 預設沒有 make

說明書要求 `make run` / `make test` / `make eval` 四個指令。

> [!CAUTION]
> **Windows 沒有 `make`**，而且本專案的 Makefile 用到 `find`、`grep`、`awk`、`rm`
> 這些 POSIX 指令，PowerShell 與 cmd 都不認得。
>
> **Windows 組員直接打下面的原始指令即可，不需要裝 make。**
> make 只是縮寫表，每個目標底下就是一行 `uv run`。

### 指令對照表（Windows 組員照這欄打）

| 說明書寫的 | 🔴 **Windows 改打這個**（macOS 兩種都行） |
|---|---|
| `make install` | `uv sync --extra dev --extra ui` |
| `make test` | `uv run pytest -q` |
| `make check` | `uv run python tools/check_boundaries.py` |
| `make run MODULE=a_tbd` | `uv run streamlit run app/ui.py -- --module=a_tbd` |
| `make run MODULE=all` | `uv run streamlit run app/ui.py -- --module=all` |
| `make eval MODULE=a_tbd` | `uv run python -m app.cli eval --module=a_tbd` |
| `make index MODULE=a_tbd` | `uv run python -m app.cli index --module=a_tbd` |
| `make selfcheck MODULE=a_tbd` | `uv run python -m app.cli selfcheck --module=a_tbd` |
| `make fmt` | `uv run ruff format . ; uv run ruff check --fix .` |

安裝 pre-commit 掛鉤（`make install` 的第二行）：

```
uv run pre-commit install
```

**真的想用 make 的話**（想完全照說明書操作）：裝 Git for Windows 之後用 **Git Bash**，再用 [scoop](https://scoop.sh) 裝 `scoop install make`。或用 WSL2。這是可選的，不是必要的。

### 🔴 補充：Windows 的 Python 預設編碼不是 UTF-8

> [!CAUTION]
> Windows 上 Python 的預設編碼是 **cp950**（繁中系統），不是 UTF-8。
> 只要有一處 `open(path)` 忘了寫 `encoding="utf-8"`，
> **19 萬筆中文語料讀進來就會變亂碼或直接拋 `UnicodeDecodeError`**。
>
> 本 repo 現有程式碼已全部指定 `encoding="utf-8"`（已檢查過），
> 但你自己寫 M1–M5 時會不斷新增檔案讀寫。**Windows 組員請設這個環境變數兜底：**
>
> PowerShell（永久生效，設完重開終端機）：
> ```
> setx PYTHONUTF8 1
> ```

設完用 `uv run python -c "import sys; print(sys.getdefaultencoding(), sys.stdout.encoding)"` 確認兩個都是 `utf-8`。

### 🔴 補充：第 5 步「盤點硬體」要多記一欄「作業系統」

原文只要求記顯示卡與記憶體。混用環境下**作業系統決定了模型後端**（Mac 走 Metal、Windows 走 CUDA 或 CPU），這會影響 S3 的決議。盤點表已在 [model-lock.md](model-lock.md) 加上該欄。

## S3 選定模型，然後鎖死不准換

### 🔴 更正：「五個人要用同一份檔案」不夠，**執行後端也要一致**

說明書強調「同一個模型有很多壓縮版本，要指定是哪一份」。這在混用環境下還不夠：

> [!CAUTION]
> 同一個嵌入模型、同一段文字，在 **Mac 的 MPS（預設 fp16）** 與
> **Windows 的 CUDA / CPU（fp32）** 上算出來的向量會有低位數值差異。
> 排序通常不受影響，但分數接近時可能讓 **Recall@5 差一兩個百分點** ——
> 那就違反了「五個人的分數要能互相比較」這個前提。
>
> **決議：`shared/models.py` 的 `embed()` 與 `rerank()` 固定 `device="cpu"`、`dtype=float32`，寫死在裡面，外面改不了。**

成本很低：嵌入只在**建索引時跑一次**（幾千筆，CPU 幾分鐘）與**每次查詢一句話**（毫秒級）。真正吃 GPU 的是地端 SLM。

### 🔴 補充：地端 SLM 走原生 Ollama，各自用自己的 GPU

| 系統 | Ollama 安裝 | 後端 |
|---|---|---|
| macOS | `brew install ollama` 或官網安裝檔 | Metal（Apple Silicon GPU） |
| Windows | 官網安裝檔（原生支援，不需要 WSL） | CUDA（NVIDIA）或 CPU |

兩邊都是 `ollama pull <模型>` 抓同一份模型檔、對同一個編號，程式統一透過 `OLLAMA_HOST=http://127.0.0.1:11434` 連過去（見 `.env.example`）。

> [!WARNING]
> **不要把地端模型放進 Docker。** Docker Desktop for Mac 無法把 Apple Silicon 的
> GPU/Metal 傳進容器，容器內只有 CPU，會慢到不能用 —— 反而讓 macOS 那台變全隊最慢。

### 🔴 補充：以最低配那台為準時，要跨 OS 比較

說明書說「以最低配的那台為準」。混用環境下要注意 **Apple Silicon 的統一記憶體** 與
**NVIDIA 的顯卡記憶體不是同一個東西**：M 系列晶片 16GB 統一記憶體大約可跑 7B 量化模型，
與 8GB 顯卡記憶體的 Windows 機相當。盤點時兩種數字都要記下來再一起判斷。

## S11 M2：自己寫截圖理解

### 🔴 更正：「五個人可以選不一樣的 OCR」要加一個但書

說明書原文允許每個人自己選 OCR 引擎。在混用環境下這會在**第六週合併時爆炸**。

> [!CAUTION]
> **OCR 引擎必須在 macOS 與 Windows 兩邊都裝得起來。**
>
> 原因見下面 S16 那節：第六週五個模組要掛在**同一台機器**上一起跑，
> 展示也是一台機器跑 `MODULE=all`。如果有人選了只在自己 OS 裝得起來的引擎，
> 他的模組在展示機上就失效。

| 引擎 | macOS (Apple Silicon) | Windows | 結論 |
|---|---|---|---|
| **RapidOCR** | ✅ ONNX Runtime，pip 直裝 | ✅ | 🔴 **建議全隊統一用這個** |
| **PaddleOCR** | 🔴 常裝不起來或要自己編譯 | ✅ | 要用的人必須先在 Mac 上驗證過 |
| **Tesseract** | 🟡 `brew install tesseract tesseract-lang` | 🟡 安裝檔 ＋ 手動設 PATH | 要裝原生二進位，兩邊步驟不同 |

### 🔴 補充：OpenCV 要裝 headless 版

```
opencv-python-headless
```

一般的 `opencv-python` 在 Linux 需要系統層的 `libGL`，**CI 跑在 ubuntu 會直接失敗**。
headless 版功能相同，只是沒有 GUI 視窗（我們本來也不需要）。

### 🔴 補充：自製截圖的字型兩邊不同

macOS 預設是**蘋方**，Windows 是**微軟正黑體**。同一段文字算出來的 CER 會有差異。

這件事**不需要修正**——五個人本來就各自出 20 張題目、各自量自己的 CER，而且字型多樣其實更接近真實使用者的截圖。但要寫進資料卡，並且記得說明書要求「五個人的截圖標註格式要在 W3 就講好」，那個必須統一。

## S16–S17 合併週：這是跨平台風險真正爆炸的地方

> [!CAUTION]
> **第六週五個模組要掛在同一台機器上一起跑（`MODULE=all`），第七週展示也是一台機器。**
> 那台機器必須裝得起**全部五個人的依賴**。
>
> 如果 B 用了只在 Windows 裝得起來的 OCR，而展示機是 macOS，**B 的模組在展示時失效**。
>
> **決議事項：S3 站立會時就指定展示機是誰的，並在 W5 結束前先試裝一次全部五個模組。**
> 不要等到第六週第一天才發現。

### 已內建的防護（最壞情況不會整個掛掉）

`m2_vision.py` 在 OCR 不可用時**降級而不是當掉**，而 `health()` 裡 OCR 那一項是
`required=False`：**裝不起來的模組仍然會被載入，只是截圖功能失效、退成純文字判讀。**

所以最壞情況是「多模態的賣點消失」，不是「整個系統掛掉」。但展示時少掉截圖那段，
等於少掉跟官方關鍵字搜尋最直觀的差別，還是要避免。

## 關於 Docker：為什麼現在不用

有人會問「用 Docker 不就全解決了嗎」。結論是 **現在不用，S11 再評估**。

| Docker 能解決 | Docker 不能解決 / 會變更糟 |
|---|---|
| ✅ OCR 的系統層依賴（libGL、Tesseract 二進位） | 🔴 **GPU**：Docker Desktop for Mac 無法傳遞 Metal，容器內只有 CPU |
| ✅ Python 版本與套件一致 —— 但 `uv.lock` 已經做到了 | 🔴 模型檔幾 GB、向量庫幾百 MB，還是要 volume 掛載 |
| ✅ 本機與 CI 完全一致 | 🔴 macOS 的 bind mount I/O 較慢，開發時 hot reload 會鈍 |
| | 🔴 七週專題要五個人都學會排除容器問題 |

**判斷跟說明書 S19 拒絕做會員系統、金流是同一個邏輯：七週的成本要花在技術主題上。**
`uv` + `uv.lock` 已經解決 Python 層的一致性，Docker 是為了系統層依賴才值得付的代價，
而那個痛點要到 S11 才會出現。

**分三層處理：**

| 層 | 做什麼 | 何時 | 狀態 |
|---|---|---|---|
| 0️⃣ | `.gitattributes` 釘死 LF | 現在 | ✅ 已完成 |
| 1️⃣ | 指令對照表 ＋ 五個人各跑一次 `pytest` 確認綠燈 | S2 收尾 | ⬜ 待四人到齊 |
| 2️⃣ | 如果 OCR 真的裝不起來，**只把 OCR 包成容器**，其餘維持原生 | S11 再評估 | ⬜ |
