## 3. 方法

| 環節 | 我的做法 | 為什麼這樣選 |
|---|---|---|
| M1 語料處理 | 讀 parquet → 標籤子字串比對（含排除）→ 平台詞內文推斷 → 去重 → 寫 `cases.jsonl`。篩選條件從 `pack.yaml` 讀，不寫死 | 標籤不是受控分類，等值比對會漏掉空白與換行變體。條件寫在 `pack.yaml` 是因為那份檔案才是模組的身分宣告，兩邊各寫一份一定會走散 |
| M2 截圖理解 | **尚未實作**，仍是範本骨架 | OCR 引擎未選（S11）。有圖時降級成純文字，不整個當掉 |
| M3 語意檢索 | bge-m3 向量（cosine／fp32）＋ facets 結構化過濾，`NumpyStore` 單檔 `.npz`。三層退路：向量 → 結構化過濾 → 字元 2-gram 重疊 | 不先上 Chroma／Qdrant 是因為那是 S12 才要決定的事，抽一層介面先用 numpy，換的時候上層不用動。⚠ Chroma 預設 L2 不是 cosine，換過去 `min_score` 會全部失效 |
| M4 判讀與抽取 | **規則硬抽（第三層退路）**，信心一律標 LOW | S13 的 prompt、12 則示範題與 grammar 約束還沒寫，`_SLM_PROMPT_READY = False`。在 prompt 真的寫出來之前不呼叫模型 —— 送空 prompt 再丟掉回覆只會浪費時間並讓 confidence 說謊 |
| M5 Agent 與行動劇本 | 自寫狀態機，六步：截圖 → 合併 → 去識別化 → 分類抽取 → 檢索 → **地端 SLM 生成白話說明**。每步包 try/except，失敗記 `degraded` 不中斷 | 第六步是 C 獨有的（A／E 沒有）。檢索與生成分開且順序不能顛倒 —— 生成要吃前一步的產出，這就是 RAG 跟「直接問模型」的差別。生成掛掉時檢索結果仍拿得出來 |

## 6. 已知限制

> 誠實揭露限制是專業度的指標。一份寫滿限制的報告，通常比一份只有漂亮數字的報告可信。

1. **`DEFAULT_MIN_SCORE = 0.60` 只用 5 個手工問句量的。** 在完整索引（10,051 筆）
   上量的分布是可信的，但校準樣本太小，S12 要用標註評測集重驗。先前在 300 筆
   demo 索引上量到 0.50，放大到 10,051 筆就不夠用了 —— 門檻不能在小索引上量完就當數。

2. **🔴 `retrieve()` 用 `label` 當去重鍵，正在丟掉最相似的案例。** 語料 91% 是同一個
   label，去重後前 5 筆裡有 4 筆被換成「小 bucket 裡的最高分」。實測（拿一筆含
   入金／出金的案例當查詢）：純相似度前 5 是 0.9203／0.9176／0.9137／0.9086／0.9079，
   去重後變成 0.9203／0.9000／0.8923／0.8708／0.8335，其中兩筆來自只有 1 筆案例的
   bucket。而且去重上限硬是 15 筆（語料只有 15 種 label），`top_k` 再大也沒用。

3. **🔴 `playbook.yaml` 仍是範本的中獎詐騙劇本**（與 `_template` 逐字相同）。階段是
   「剛收到通知／被要求先付錢／已經匯款」，`cues` 是 `[收到, 通知, 簡訊, 中獎]`。
   投資詐騙受害者會講的「入金」「出金」「老師」「保證金」一個都不命中，所以
   `detect_stage()` 永遠 fallback 到 `contacted`（risk=medium）。後果是連鎖的：風險
   等級低報 → 行動清單給的是中獎詐騙的行動 → `generation.explain()` 拿到的
   `stage_name` 也錯，模型在錯誤前提上寫說明。

4. **`eval/route_questions.yaml` 仍是範本的 2 題**，與本模組無關，且 `gold_case_ids`
   全空 → `evaluate.py` 的 `recall_at_5` 與 `mrr_at_10` 整段不會執行。

5. **餵給生成模型的只有 120 字開頭。** `search()` 固定 `excerpt=safe.text[:120]`，
   但語料 p50 是 285 字、**98% 超過 120 字**。`generation` 只放 3 筆，所以模型看到的
   是三段被砍掉的開頭 —— 而開頭多半在講「怎麼認識對方」，真正有價值的「如何拖延
   出金」「第二筆用什麼理由要」都在後半段被切掉。

6. **有 `filters` 時會繞過 `min_score`。** `retrieve()` 在有過濾條件時把門檻設為 0，
   而詞彙表裡是「投資」「廣告」「轉帳」這類極常見的詞（`CATEGORY['假投資']` 含
   「投資」、`CHANNEL['網頁廣告']` 含「廣告」），幾乎每個問句都抽得出條件 ——
   等於門檻**常態是關的**。離題問句只要碰巧含一個詞就會繞過去。

7. **`target` facet 有 95.3% 抽不出來。** 使用者問「長者被騙投資」會抽出
   `target=長者` → 篩到 25 筆（0.2%）→ 而門檻已被放掉 → 回一批分數很低、但每筆
   都帶案例編號與縣市、看起來非常像真的結果。

8. **facets 推斷的準確率從未量過。** 漏抓與錯抓兩種相反的錯誤都只有註解描述，
   沒有數字。已知 17.5% 的案例帶到第二個 `category`（多半是內文提了一句「我原本
   在找工作」就被當成求職詐騙），那是推斷誤判不是真的跨類。

9. **`numpy` 與 `pyarrow` 都不在宣告的相依裡。** `numpy` 是 `ml` 那組的 torch 順便
   帶進來的，`pyarrow` 靠 `streamlit` 的傳遞相依 —— 照 README 跑 `make install`
   的機器兩個都可能沒有。兩者現在都走延遲 import，`numpy` 缺席時丟
   `ModelDependencyError`，`search()` 現成的 except 接得住並退到第 3 層，所以不會
   炸在使用者面前。

   **但這是繞過去，不是修好**：CI 跑的是 `uv sync --extra dev`（沒有 numpy），
   所以 **CI 從來沒有真正執行過向量檢索那條路徑** —— 綠燈只證明關鍵字退路沒壞。
   向量那條目前只有本機驗證過。

10. **`evaluate.py` 的 `latency_p95_s` 量錯對象。** 它計時的是 `can_handle()`
    （純關鍵字比對，極快），但 S12 那個 ≤ 1 秒門檻指的是**查詢延遲**。照現在的寫法
    這一項會無條件過關，量不出檢索真正的延遲。

11. **`search()` 每次呼叫都重建 `Retriever`。** 等於每查一次就重讀 63 MB 的 npz
    並重新解析 10,051 行 JSONL。目前不影響正確性，但延遲預算吃光就塞不下重排序。

12. **M2 完全沒有實作。** OCR 引擎未選（S11），有截圖時只會降級成純文字，
    `health()` 的 `ocr` 項會回 not ok（`required=False`，不擋啟動）。
