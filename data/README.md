# 語料放哪裡

大檔案絕對不要進 GitHub（說明書 §1.6）。這個資料夾在版控裡是空的，只留這份說明。

| 東西 | 放哪裡 | 大小 |
|---|---|---|
| 共用語料 `corpus.parquet`（正規化後的合併檔） | 共用雲端硬碟 | 幾十～上百 MB |
| 模型檔（GGUF 等） | 各自本機下載，對編號 | 幾 GB |
| 向量資料庫 | 各自本機建（`make index MODULE=…`） | 幾百 MB |

抓下來之後放到本機任一位置，然後在 `.env` 裡指定路徑：

```
CORPUS_PARQUET=/你的路徑/corpus.parquet
```

## 語料來源：不綁死單一來源

**165 是主語料，不是唯一來源。** 程式只認下面這個正規化後的形狀，任何來源
只要能映射成它就接得進來。

### 正規化 schema

`packages/modules/*/m1_corpus.py` 的 `Case`，以及契約層的 `SimilarCase`：

| 欄位 | 必要 | 說明 |
|---|:--:|---|
| `case_id` | ✅ | 該來源內部的案例編號 |
| `source` | ✅ | **來自哪個來源**。混來源時 `case_id` 會撞號——兩份資料各自從 1 開始編很正常，所以出處是 `source` + `case_id`，不是 `case_id` 自己 |
| `text` | ✅ | 案例內文 |
| `label` | | 手法分類。各來源的體系不同，見下方「難題一」 |
| `date` | | 案件日期 |
| `county` | | 縣市 |

> [!IMPORTANT]
> `source` 預設是 `"165"`。**加別的來源時務必明寫**，忘了寫會被默默標成 165，
> 而這種錯很難在事後發現。

### ⚠ 抓取時會遇到的坑

一頁 20,000 筆約 31 MB，**實測連線會在中途斷掉**。斷點若落在 `\uXXXX`
中間，`json` 會報 `Invalid \uXXXX escape` —— 看起來像上游資料壞掉，
其實是讀取不完整。已驗證：重抓同一頁，資料是乾淨的。

`fetch_corpus_165.py` 因此會比對 `Content-Length` 並重試（最多 4 次，
遞增退避）。實際抓取時第 1 頁就連續失敗兩次才成功，這段不是預防性設計。

### 🔴 標籤體系很亂，S9 之前一定要處理

`CaseTitle` 是官方標的手法分類，但**原始資料有 1,003 種不同寫法**：

| 門檻 | 手法數 | 涵蓋 |
|---|---:|---:|
| ≥ 10,000 筆 | 4 | 49.6% |
| ≥ 5,000 筆 | 7 | 61.8% |
| **≥ 2,000 筆** | **21** | **86.7%** |
| ≥ 100 筆 | 64 | 98.4% |
| 全部 | 1,003 | 100% |

長尾極長：939 種不到 100 筆，合計才 3,102 筆；**674 種只出現一次**。

亂的來源有兩類，處理方式不同：

**一、純格式變體（機器可自動合併）**

去掉前後空白、統一全形半形括號之後，**50 組會合併，涉及 191 種原始寫法**。
例：`網路購物詐騙` 有 9 種寫法（含 `'\n \t\n網路購物詐騙'`、
`'網路購物詐騙               '`）。這就是 `pack.yaml` 的 `label_aliases`
要處理的東西。

**二、語意重複（要人判斷，不能自動合併）**

| 寫法 A | 寫法 B | 合併後 |
|---|---|---|
| 假投資詐騙 27,718 | 假投資 2,509 | 30,227 |
| 網路購物詐騙 44,250 | 假網拍 4,825 | 49,075 |
| 釣魚簡訊(惡意連結)詐騙 3,468 | 釣魚連結詐騙 3,006 | 6,474 |
| 假借銀行貸款詐騙 3,939 | 假借銀行貸款詐財詐騙 2,037 | 5,976 |

**這幾組合不合併會直接改變交叉表的筆數，進而改變誰能過 2,000 筆門檻。**
所以這是全隊共同決定，不是各自處理 —— 五個人各合一套，模組之間就再也
比不了分數。

## 加第二個來源要做什麼

**TODO(S6)**：目前只有 165。要加來源的人照這張清單走：

- [ ] 在本檔開一節，寫明：**來源名稱 / 取得方式 / 抓取日期 / 規模 / 原始欄位**
- [ ] 寫一支映射程式，把原始欄位轉成上面的 schema，`source` 填一個**簡短固定的識別字**（例：`165`、`police-open`）
- [ ] **對齊標籤體系**（見難題一）
- [ ] 確認**使用條款**允許本專題的用法（見下方「使用界線」）
- [ ] 合併進 `corpus.parquet`，並把該來源的筆數記在這裡

### 難題一：標籤體系不會一樣

165 的 `標籤` 是官方標好的手法分類，這是它最大的價值。**別的來源幾乎不可能
用同一套分類。**

所以混來源時，`pack.yaml` 的 `labels_canon` 與 `label_aliases` 要從「165 內部
的各種寫法」擴充成「**跨來源的對映表**」。這是全隊共同決定，不是各自處理——
五個人各對一套，模組之間就再也比不了分數。

### 難題二：平台欄位多半要用推斷的

165 **沒有「平台」這個欄位**。平台是從 `內文` 用關鍵詞比對推斷出來的
（`pack.yaml` 的 `platform_terms`）。別的來源大概也一樣。

這代表「平台 × 手法」的交叉表，手法軸可以直接 group by 標籤，**平台軸得先
定義一組關鍵詞才算得出來**——而關鍵詞定義會直接影響每一格的筆數，進而影響
`pack.yaml` 的 `stats.platform_cases` 有沒有過 2,000 筆門檻。

**先抓語料、先做交叉表，再分配組合。** 反過來做等於在沒有數據的情況下決定。

## 使用界線

**使用條款是逐來源的，不能一體適用。** 加新來源時要各自確認，並寫在該來源那一節。

165 案例內文是真實受害者的第一人稱敘述。只在專題內部用，
展示一律用節錄或改寫，絕不投影原文。
