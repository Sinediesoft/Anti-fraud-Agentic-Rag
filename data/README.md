# 語料放哪裡

大檔案絕對不要進 GitHub（說明書 §1.6）。這個資料夾在版控裡是空的，只留這份說明。

| 東西 | 放哪裡 | 大小 |
|---|---|---|
| 共用語料 `corpus.parquet`（正規化後的合併檔） | 共用雲端硬碟 | 幾十～上百 MB |
| 模型檔（GGUF 等） | 各自本機下載，對編號 | 幾 GB |
| 向量資料庫 | 各自本機建（`make index MODULE=…`） | 幾百 MB |

抓下來之後放到本機任一位置，然後在 `.env` 裡指定路徑：

```
CORPUS_PARQUET=/你的路徑/corpus.parquet
```

## 語料來源：不綁死單一來源

**165 是主語料，不是唯一來源。** 程式只認下面這個正規化後的形狀，任何來源
只要能映射成它就接得進來。

### 正規化 schema

`packages/modules/*/m1_corpus.py` 的 `Case`，以及契約層的 `SimilarCase`：

| 欄位 | 必要 | 說明 |
|---|:--:|---|
| `case_id` | ✅ | 該來源內部的案例編號 |
| `source` | ✅ | **來自哪個來源**。混來源時 `case_id` 會撞號——兩份資料各自從 1 開始編很正常，所以出處是 `source` + `case_id`，不是 `case_id` 自己 |
| `text` | ✅ | 案例內文 |
| `label` | | 手法分類。各來源的體系不同，見下方「難題一」 |
| `date` | | 案件日期 |
| `county` | | 縣市 |

> [!IMPORTANT]
> `source` 預設是 `"165"`。**加別的來源時務必明寫**，忘了寫會被默默標成 165，
> 而這種錯很難在事後發現。

- [ ] 合併進 `corpus.parquet`，並把該來源的筆數記在這裡

### 難題一：標籤體系不會一樣

165 的 `標籤` 是官方標好的手法分類，這是它最大的價值。**別的來源幾乎不可能
用同一套分類。**

所以混來源時，`pack.yaml` 的 `labels_canon` 與 `label_aliases` 要從「165 內部
的各種寫法」擴充成「**跨來源的對映表**」。這是全隊共同決定，不是各自處理——
五個人各對一套，模組之間就再也比不了分數。

### 難題二：平台欄位多半要用推斷的

165 **沒有「平台」這個欄位**。平台是從 `內文` 用關鍵詞比對推斷出來的
（`pack.yaml` 的 `platform_terms`）。別的來源大概也一樣。

這代表「平台 × 手法」的交叉表，手法軸可以直接 group by 標籤，**平台軸得先
定義一組關鍵詞才算得出來**——而關鍵詞定義會直接影響每一格的筆數，進而影響
`pack.yaml` 的 `stats.platform_cases` 有沒有過 2,000 筆門檻。

**先抓語料、先做交叉表，再分配組合。** 反過來做等於在沒有數據的情況下決定。

## 使用界線

**使用條款是逐來源的，不能一體適用。** 加新來源時要各自確認，並寫在該來源那一節。

165 案例內文是真實受害者的第一人稱敘述。只在專題內部用，
展示一律用節錄或改寫，絕不投影原文。
